# CommonMark 规范里最坑的 12 个边界案例

写 Markdown 觉得简单，是因为你只用了"正常情况"。真正让解析器打架的，是边界。

下面 12 个案例全部来自规范讨论与真实踩坑，每条给出"你以为的"和"实际上的"。

## 案例 1：两个星号紧贴中文

```markdown
这是一句**加粗**的话。
这是**这句**也加粗吗？
```

- 一般认为没问题，但部分解析器要求星号内侧不能紧跟标点
- **可靠写法**：加粗两侧留空格，或整段只用一处加粗

## 案例 2：下划线与变量名

```markdown
请设置 my_var_name 的值。
```

- `snake_case` 里的下划线在某些解析器里会被当成"强调"起始
- **可靠写法**：变量名放进行内代码

## 案例 3：列表项之间的空行

```markdown
- 第一项

- 第二项
```

- **宽松列表**：一项一个段落，间距大
- **紧凑列表**：连在一起，间距小
- 同一篇文章里两种混用，观感会不一致

## 案例 4：列表里放代码块

```markdown
1. 安装依赖：

       npm install

2. 启动服务
```

- 代码块必须缩进 **4 个空格**（相对列表内容缩进）
- 缩进少了会被并进上一段文字

## 案例 5：序号从 2 开始

```markdown
2. 第二步
3. 第三步
```

- 解析器会**自动从 1 开始编号**，你写的数字不保证被采用
- 需要固定编号时，用显式数字 + 不用列表标记

## 案例 6：引用里再放引用

```markdown
> 外层
>
> > 内层
```

- 空行里也要带 `>`，否则内层引用会被截断
- 三层以上建议改写成小标题 + 段落

## 案例 7：表格里的竖线

```markdown
| 表达式 | 说明 |
| --- | --- |
| a \| b | 按位或 |
```

- 单元格内的 `|` 必须转义成 `\|`
- 不转义会把一列拆成两列

## 案例 8：代码块里出现三个反引号

要展示三个反引号，用**四个反引号**开外层：

    ````
    ```
    内层三个反引号就是普通字符
    ```
    ````

- 这是规范明确支持的写法，但很多编辑器不提示
- 少于四个反引号时，内层三个会把代码块提前结束

## 案例 9：链接地址里有括号

```markdown
[维基条目](https://en.wikipedia.org/wiki/Markdown_(language))
```

- 括号会提前结束链接
- **可靠写法**：用参考式，或用 `%28`/`%29` 编码

## 案例 10：以数字开头的行被当成列表

```markdown
2024. 这一年发生了很多事。
```

- 会被解析成"有序列表第 2024 项"
- **可靠写法**：句首加反斜杠转义 `2024\.`

## 案例 11：缩进 1~3 个空格

```markdown
 这段前面有两个空格。
```

- 1~3 个空格是"无意义缩进"，仍属段落
- **4 个空格**才会变成代码块
- 混排时最容易出现"莫名变成代码"的问题

## 案例 12：HTML 块与 Markdown 混排

```markdown
<div>
**这段不会加粗**
</div>

<div>
  
**这段会加粗**
</div>
```

- HTML 块内部的 Markdown **默认不解析**
- 想让它解析，块内首尾各留一个空行

## 一份"防坑检查表"

| 场景 | 检查点 |
|---|---|
| 加粗/斜体不生效 | 星号内侧是否有空格 |
| 列表被合并 | 列表前是否空行、项间是否空行 |
| 代码块跑到段落里 | 是否缩进满 4 空格 |
| 表格错列 | 是否有未转义的竖线 |
| 链接被截断 | 地址里是否有括号 |
| 文字莫名变大 | 行首是否有 `#` 或数字点号 |

## 为什么要关心这些

因为**你的 Markdown 会经过多个解析器**：

```text
编辑器预览  →  本站导出（marked）
                    ↓
公众号 / 知乎 / 掘金 各自的解析器
                    ↓
最终读者看到的排版
```

每多一个解析器，就多一次"边界分歧"的机会。守住这 12 条，跨平台一致性会明显提升。
