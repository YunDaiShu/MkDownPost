# Markdown 生态：标准、方言与发布路径

## 一、为什么会有"方言"问题

Markdown 最初只有一份语法说明和一个 Perl 实现，很多边界情况没定义：

- `*` 和 `_` 在中文里算不算强调？
- 列表项之间空行会不会被拆成两个列表？
- 表格的 `|` 在代码里要不要转义？

不同解析器给出不同答案，于是出现了方言。

## 二、CommonMark：把边界情况定死

2014 年起，社区开始推动 CommonMark 规范：

- 用**测试用例**（几千条）固定每种输入的正确输出
- 提供参考实现与一致性测试工具
- 明确列表嵌套、强调优先级、HTML 块等模糊地带

现在很多编辑器/平台底层都用 CommonMark 兼容解析器。

## 三、GFM：GitHub 方言

GFM = CommonMark + 一组扩展：

| 扩展 | 语法 |
|---|---|
| 表格 | `\| a \| b \|` |
| 任务列表 | `- [x]` |
| 删除线 | `~~文字~~` |
| 自动链接 | 直接写 URL |
| 代码块语言 | `\`\`\`js` |

本站采用 GFM 语法集，因为它是目前跨平台兼容性最好的子集。

## 四、发布路径：一份 Markdown 去哪

```text
              ┌─→ HTML（博客 / 静态站）
Markdown ─────┼─→ 公众号（全内联样式）
              ├─→ 小黑盒 / TapTap（结构 + 图片规则）
              ├─→ PDF（打印 / 归档）
              └─→ Word（交付 / 二次编辑）
```

关键点：**内容与排版分离**。同一份 .md 换主题、换平台，正文一个字都不用改。

## 五、各平台的差异（实务经验）

| 平台 | 特点 | 注意 |
|---|---|---|
| 公众号 | 只认内联样式，会过滤 `<style>` | 表格与代码块样式要内联；外链可能被吞 |
| 小黑盒 | 标题层级显示弱，图片要求 16:9 更佳 | 4 级以上标题建议降级为加粗 |
| TapTap | 表格/任务列表支持不稳定 | 自动降级为文本更安全 |
| 知乎 | 代码块与表格需限宽 | 公式不解析 |
| 掘金 / CSDN | 自带编辑器与高亮 | 粘贴后语言可能被重置 |
| GitHub | 原生 GFM，Mermaid 可直接渲染 | 相对路径图片有效 |

## 六、写长文时的工程化做法

1. **一个文件一个主题**，文件名用 slug（`markdown-what-is.md`）
2. **索引文件**登记元信息（标题、摘要、标签、是否精选）
3. **图片集中放** `assets/img/`，用相对路径，方便迁移
4. **不写死样式**，排版交给主题
5. **用 Git 管理**，每次改动都有记录

本站的 `content/` + `content-index.json` 就是这个思路：**新增文章只需放一个 .md 并登记一行**。

## 七、Markdown 的边界

它不是万能的，遇到这些情况要认清：

- **精确排版**：交给专业排版工具
- **复杂表格**：退回 HTML 或图片
- **强交互**：那是组件与脚本的领域
- **协同编辑**：需要 CRDT/OT 一类的系统

认清边界，比"用 Markdown 做一切"更专业。

## 八、如果你想继续深入

- 读 CommonMark 规范里的 **spec.txt**（每条规则都有正反例）
- 看一个解析器的实现（marked / markdown-it），理解 token 流
- 试着写一个"只支持 6 种语法"的最小解析器，你会立刻明白边界情况有多麻烦

> 一句话总结：Markdown 的价值不在语法，而在**它把写作从排版里解放出来**。
