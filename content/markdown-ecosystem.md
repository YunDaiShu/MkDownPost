# Markdown 生态：标准、方言与发布路径

## 一、为什么会有"方言"问题

Markdown 最初只有一份语法说明和一个 Perl 实现，很多边界情况没定义：

- `*` 和 `_` 在中文里算不算强调？
- 列表项之间空行会不会被拆成两个列表？
- 表格的 `|` 在代码里要不要转义？

不同解析器给出不同答案，于是出现了方言。

## 二、CommonMark：把边界情况定死

2014 年起，社区开始推动 CommonMark 规范：

- 用**测试用例**（几千条）固定每种输入的正确输出
- 提供参考实现与一致性测试工具
- 明确列表嵌套、强调优先级、HTML 块等模糊地带

现在很多编辑器/平台底层都用 CommonMark 兼容解析器。

## 三、GFM：GitHub 方言

GFM = CommonMark + 一组扩展：

| 扩展 | 语法 |
|---|---|
| 表格 | `\| a \| b \|` |
| 任务列表 | `- [x]` |
| 删除线 | `~~文字~~` |
| 自动链接 | 直接写 URL |
| 代码块语言 | `\`\`\`js` |

本站采用 GFM 语法集，因为它是目前跨平台兼容性最好的子集。

## 四、发布路径：一份 Markdown 去哪

```text
              ┌─→ HTML（博客 / 静态站）
Markdown ─────┼─→ 公众号（全内联样式）
              ├─→ 小黑盒 / TapTap（结构 + 图片规则）
              ├─→ PDF（打印 / 归档）
              └─→ Word（交付 / 二次编辑）
```

关键点：**内容与排版分离**。同一份 .md 换主题、换平台，正文一个字都不用改。

## 五、各平台的差异（实务经验）

| 平台 | 特点 | 注意 |
|---|---|---|
| 公众号 | 只认内联样式，会过滤 `<style>` | 表格与代码块样式要内联；外链可能被吞 |
| 小黑盒 | 标题层级显示弱，图片要求 16:9 更佳 | 4 级以上标题建议降级为加粗 |
| TapTap | 表格/任务列表支持不稳定 | 自动降级为文本更安全 |
| 知乎 | 代码块与表格需限宽 | 公式不解析 |
| 掘金 / CSDN | 自带编辑器与高亮 | 粘贴后语言可能被重置 |
| GitHub | 原生 GFM，Mermaid 可直接渲染 | 相对路径图片有效 |

## 六、写长文时的工程化做法

1. **一个文件一个主题**，文件名用 slug（`markdown-what-is.md`）
2. **索引文件**登记元信息（标题、摘要、标签、是否精选）
3. **图片集中放** `assets/img/`，用相对路径，方便迁移
4. **不写死样式**，排版交给主题
5. **用 Git 管理**，每次改动都有记录

本站的 `content/` + `content-index.json` 就是这个思路：**新增文章只需放一个 .md 并登记一行**。

## 七、Markdown 的边界

它不是万能的，遇到这些情况要认清：

- **精确排版**：交给专业排版工具
- **复杂表格**：退回 HTML 或图片
- **强交互**：那是组件与脚本的领域
- **协同编辑**：需要 CRDT/OT 一类的系统

认清边界，比"用 Markdown 做一切"更专业。

## 八、如果你想继续深入

- 读 CommonMark 规范里的 **spec.txt**（每条规则都有正反例）
- 看一个解析器的实现（marked / markdown-it），理解 token 流
- 试着写一个"只支持 6 种语法"的最小解析器，你会立刻明白边界情况有多麻烦

> 一句话总结：Markdown 的价值不在语法，而在**它把写作从排版里解放出来**。

## 附：一次"同一份内容发四个平台"的实操记录

**素材**：一篇 1200 字教程，含 1 张图、1 个 3 列表格、2 个代码块。

| 平台 | 处理动作 | 耗时 | 结果 |
|---|---|---|---|
| 公众号 | 导出内联 HTML → 全选粘贴 | 5 分钟 | 样式保留，图片需重新确认 |
| 小黑盒 | 导出适配 → 去掉 h4 级标题 | 3 分钟 | 标题统一为加粗 |
| TapTap | 导出适配 → 表格降级为等宽文本 | 2 分钟 | 手机端不再横向溢出 |
| GitHub README | 直接提交 .md | 1 分钟 | 原生 GFM 正常 |

结论：**内容只需写一遍，差异集中在最后一步转换**。

## 附：为什么"全内联样式"是公众号的唯一解

公众号编辑器在粘贴时会做一次富文本清洗：

1. 移除 style 与 script 标签
2. 移除 class / id 属性
3. 只保留行内 style 中它认识的部分（颜色、字号、间距、边框）
4. 图片地址重写为自己的 CDN

所以导出器必须做两件事：**把 CSS 计算成行内样式**、**把结构简化到它认识的标签**。

## 附：Markdown 之外的替代方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| Markdown | 纯文本、Git 友好、生态广 | 排版能力有限 |
| AsciiDoc | 结构更丰富（脚注、目录、包含） | 学习成本高、工具少 |
| reStructuredText | 文档工程化（Sphinx） | 语法繁琐 |
| HTML 直写 | 能力上限最高 | 写作体验差 |
| Word / 在线文档 | 所见即所得 | 版本管理差、难复用 |

## 附：多平台发布决策表

    内容 > 2000 字 or 需长期维护 ?
      ├─ 是 → Markdown（本机写作 + 版本管理）
      └─ 否 → 直接用目标平台编辑器

    同一内容要发 ≥ 2 个平台 ?
      ├─ 是 → Markdown + 导出适配器
      └─ 否 → 单平台编辑器即可

    需要精确排版 / 印刷 ?
      ├─ 是 → Markdown 只作草稿，终稿进排版软件
      └─ 否 → Markdown 全流程
